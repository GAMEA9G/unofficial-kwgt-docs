KWGT file structure

A KWGT preset is a structured document containing metadata, a root layer, child modules, optional global variables and internal events. A packaged .kwgt file additionally contains the preset JSON and any required resources.

This page documents the observed structure of KWGT preset files. Properties are classified according to their observed usage. An undocumented property should not be assumed to be invalid simply because its purpose is unknown.

1. Basic preset structure

The main preset document contains two important top-level properties: preset_info and preset_root. 

{
  "preset_info": {
    "version": 13,
    "title": "My Widget",
    "description": "My custom KWGT preset",
    "author": "Author",
    "email": "",
    "width": 400,
    "height": 200
  },
  "preset_root": {
    "internal_type": "RootLayerModule",
    "viewgroup_items": []
  }
}

This is a simplified structural example, not a guarantee that every KWGT version will accept a preset containing only these properties.

2. Top-level properties

Property Purpose Status
preset_info Preset metadata and configuration. Observed
preset_root Root module containing the widget's layers. Observed

2.1 preset_info

Contains metadata about the preset, including its version, display information and dimensions.

Property Description Notes
version Preset format version. Version 13 is used in the documented examples. Versions 11 and 12 also appear in real presets.
title Preset display name. Used to identify the preset.
description Preset description. Preserve if present.
author Author information. Preserve if present.
email Author email. May be empty.
width Preset width. Observed in generated presets.
height Preset height. Observed in generated presets.
locked Preset editing lock. Observed as a boolean.
features Preset feature tags. Examples include MUSIC, NOTIFICATIONS and BLUETOOTH.
release Internal metadata. Purpose not fully documented.
archive Internal metadata. Purpose not fully documented.
pflags Internal flags. Purpose not fully documented.
xscreens Internal screen configuration. Purpose not fully documented.
yscreens Internal screen configuration. Purpose not fully documented.

Important: dimensions

Do not assume that width and height are always present in a real preset.

Some observed presets, including the Calendar example, omit these properties and instead calculate dimensions through formulas such as: 

$si(rwidth)$
$si(rheight)$

This indicates that the actual rendering dimensions may depend on the widget's assigned home-screen size.

  • Do not automatically insert dimensions when importing a preset.
  • Do not assume zero dimensions are valid.
  • Do not assume missing dimensions mean a broken preset.
  • Preserve existing dimension-related properties.

The complete mapping between preset dimensions and Android home-screen widget dimensions remains undocumented.

3. Root module

preset_root represents the root container of a widget. It holds the modules that make up the preset. 

{
  "preset_root": {
    "internal_type": "RootLayerModule",
    "viewgroup_items": [],
    "globals_list": {},
    "internal_events": [],
    "config_scale_value": 1
  }
}
Property Description Notes
internal_type Identifies the root module type. Widget root uses RootLayerModule.
viewgroup_items Contains child modules. Defines the layer hierarchy.
globals_list Global variables. Observed as an object.
internal_events Internal event definitions. Used for root-level interactions.
config_scale_value Editor scale configuration. Not required in every observed example.

4. Layer hierarchy

The viewgroup_items array stores the child modules of a layer or container.

A simplified example: 

{
  "internal_type": "RootLayerModule",
  "viewgroup_items": [
    {
      "internal_type": "ShapeModule"
    },
    {
      "internal_type": "TextModule"
    },
    {
      "internal_type": "BitmapModule"
    }
  ]
}

Layer ordering

In the observed preset structure, the first item in a viewgroup_items list is the bottom layer. Later items are rendered above earlier items.

Example: 

[
  { "internal_type": "ShapeModule" },
  { "internal_type": "TextModule" }
]

The shape is below the text in this example.

Nested containers

Containers can hold their own child modules. This creates a hierarchy rather than a flat list of independent layers. 

{
  "internal_type": "RootLayerModule",
  "viewgroup_items": [
    {
      "internal_type": "OverlapLayerModule",
      "viewgroup_items": [
        {
          "internal_type": "ShapeModule"
        },
        {
          "internal_type": "TextModule"
        }
      ]
    }
  ]
}

The example illustrates the nesting relationship. A complete valid module requires the additional properties expected by the corresponding KWGT module type.

5. Module types

The internal_type property identifies the type of module represented by an object.

Examples observed or used in this documentation:

Module Purpose
RootLayerModule Widget root.
KomponentModule Komponent root.
ShapeModule Shape layer.
TextModule Text layer.
BitmapModule Image or bitmap layer.
OverlapLayerModule Overlap container.

This is not a complete module registry. Do not reject an imported module merely because its type is not listed here.

6. Globals and internal events

The root module can contain global variables and internal event definitions.

6.1 globals_list

Globals provide reusable values throughout a preset. Their complete schema depends on the global type. 

{
  "globals_list": {}
}

See Toggles and globals for the available global types and their properties.

6.2 internal_events

Internal events represent interactions associated with a preset or module. 

{
  "internal_events": []
}

Do not assume every event requires an explicit type property. Some observed structures omit it.

See Events and taps for event definitions and tap actions.

7. The .kwgt package

A .kwgt file is distributed as a package containing preset data and potentially additional resources.

The documented package layout: 

MyWidget.kwgt
│
├── preset.json
│
├── preset_thumb_portrait.jpg
├── preset_thumb_landscape.jpg
│
├── bitmaps/
│   └── ...
│
├── fonts/
│   └── ...
│
└── icons/
    └── ...
File / Directory Description Status
preset.json Main preset definition. Required in the documented package layout.
preset_thumb_portrait.jpg Portrait preview image. Observed.
preset_thumb_landscape.jpg Landscape preview image. Observed.
bitmaps/ Bundled image resources. Optional.
fonts/ Bundled font resources. Optional.
icons/ Icon resources. Optional.

This is an observed layout, not an exhaustive specification of every file KWGT may store in a package.

8. Resource references

Bundled resources can be referenced through KWGT resource paths.

8.1 Bundled resources

kfile://org.kustom.provider/widgets/MyWidget.kwgt/fonts/Custom.ttf

The example points to a font stored inside the preset package.

8.2 Built-in resources

kfile://org.kustom.provider/fonts/ProductSans-Medium.ttf

Built-in resources use the provider's font directory rather than a widget package directory.

Resource handling rules

  • Preserve existing resource paths when importing a preset.
  • Do not assume a resource is embedded just because a reference exists.
  • Check that referenced resources exist before exporting.
  • Preserve the original package name when required by a resource path.
  • Do not rewrite resource references without understanding their format.

Renaming a package can break references that contain its original filename. The exact resource resolution rules should be tested against real KWGT exports.

9. Importing and exporting presets

A compatible editor must distinguish between reading a preset, modifying its data and generating a package.

9.1 Import process

  1. Identify whether the input is a raw JSON document or a ZIP-based .kwgt package.
  2. If it is an archive, locate and read preset.json.
  3. Parse the JSON without modifying the original data.
  4. Identify preset_info and preset_root.
  5. Build a representation of the module hierarchy.
  6. Resolve resource references without discarding their original paths.
  7. Keep unsupported properties and modules intact.

9.2 Editing process

An editor should modify only the properties that the user explicitly changes.

  • Do not reconstruct the entire preset from a limited editor model.
  • Do not remove properties that the editor does not understand.
  • Do not silently replace unknown module types.
  • Preserve nested hierarchy and array ordering.
  • Preserve unknown metadata and resource references.

9.3 Export process

  1. Serialize the modified preset JSON.
  2. Preserve unsupported and unmodified properties.
  3. Include all required resource files.
  4. Preserve the expected archive directory structure.
  5. Create the ZIP-based package with the correct .kwgt extension.
  6. Validate the resulting archive.
  7. Test the exported package in KWGT itself.

10. Compatibility and version handling

Preset format versions must not be confused with the version of the editor that created or modified the preset.

Version Observation Compatibility
11 Found in real preset files. Differences not fully documented.
12 Found in real preset files. Differences not fully documented.
13 Used in documented examples. Reference version for this documentation.

Do not automatically upgrade an imported preset's version number without understanding the format changes involved.

A version number alone does not prove that a preset is compatible with every KWGT release.

11. Validation checklist

Use this checklist when developing a preset parser, editor or exporter.

  • Confirm that the JSON is syntactically valid.
  • Confirm that the expected top-level properties exist.
  • Check that the root module has the expected structure.
  • Validate child module arrays.
  • Preserve unknown module types.
  • Preserve unknown properties.
  • Check nested container relationships.
  • Preserve layer ordering.
  • Check resource references.
  • Check that required archive entries exist.
  • Test the package in the actual KWGT application.

12. Common implementation mistakes

Mistake Correct approach
Rebuilding imported JSON using only known properties. Preserve the original JSON structure and modify only intended properties.
Removing unknown fields. Keep unknown fields until their behavior is understood.
Assuming every preset has width and height. Handle presets that use runtime sizing formulas.
Assuming every module is a root-level module. Support nested containers and child hierarchies.
Assuming valid JSON means a valid KWGT preset. Validate the archive and test the preset in KWGT.
Changing the archive filename without checking resource references. Preserve package-dependent paths or update them carefully.
Assuming undocumented properties are unnecessary. Preserve them and mark their behavior as unknown.

13. Known limitations

This documentation describes observed structures rather than a complete official KWGT serialization specification.

  • The complete schema for every module is not documented.
  • The exact relationship between canvas dimensions and home-screen dimensions is unknown.
  • The full set of preset version differences is unknown.
  • The complete archive resource resolution process is not documented.
  • Optionality of some metadata and thumbnail files needs further testing.

Properties whose behavior has not been verified should be treated as unknown, not invalid.
